2.3.1 Defensive design

Defensive design means designing a program so it keeps working properly even when users make mistakes or try to misuse it.

Anticipating misuse

Think ahead about what could go wrong, and plan for it: a user typing letters where a number is expected; dividing by zero; entering a negative quantity; leaving a box blank; entering a huge amount of text; trying SQL injection; guessing passwords over and over.

Authentication

Authentication confirms the identity of a user before they are allowed access. Methods: username and password; limiting the number of login attempts; two-factor authentication (e.g. a code sent to your phone); biometrics (fingerprint, face).

Input validation

Validation checks that input data is sensible and reasonable (meets set rules) before it is processed. It can't check that data is correct: an age of 15 passes a range check even if the user is really 16.

CheckWhat it checksExample
Range checkThe value is within an allowed rangeA test mark is between 0 and 100
Type checkThe data is the right data typeA quantity is a whole number, not "six"
Length checkThe data has an allowed number of charactersA password is at least 8 characters
Presence checkSomething has been entered (it isn't blank)A surname must be entered
Format checkThe data follows a set patternA date is DD/MM/YYYY; an email contains @

ERL

age = input("Enter age (11-18): ")
while age == "" OR int(age) < 11 OR int(age) > 18
    print("Invalid: enter 11 to 18")
    age = input("Enter age (11-18): ")
endwhile
print("Age accepted")

PY

def get_age():
    while True:
        entry = input("Enter age (11-18): ")
        if entry == "":
            print("Presence check failed: you must enter something")
        elif not entry.isdigit():
            print("Type check failed: whole numbers only")
        elif int(entry) < 11 or int(entry) > 18:
            print("Range check failed: must be 11 to 18")
        else:
            return int(entry)

age = get_age()
print("Age accepted:", age)

Maintainability

Maintainable code is easy for another programmer (or you, months later) to read, understand, fix and improve.

TechniqueWhy it helps
Sub programsCode is split into small, named parts that can be understood, tested and changed one at a time, and reused
Naming conventionsMeaningful names (total_price, not x) explain what each variable holds; a consistent style (e.g. camelCase or snake_case, capitals for constants)
IndentationShows which code is inside each loop, selection or sub program, so the structure is clear
CommentsExplain what sections of code do and why, without affecting how the program runs
ConstantsA value that might change, e.g. a discount rate, is updated in one place

# Sale price: 20% off, plus £5 off orders over £50
DISCOUNT = 0.2
BIG_ORDER = 50
BIG_ORDER_SAVING = 5

def sale_price(price):
    new_price = price * (1 - DISCOUNT)
    if new_price > BIG_ORDER:
        new_price = new_price - BIG_ORDER_SAVING
    return new_price

price = float(input("Price: "))
print(sale_price(price))

2.3.2 Testing

The purpose of testing is to check the program works as intended and meets the requirements, to find and remove errors, and to make sure it handles invalid input without crashing.

Type of testingWhenWhat
Iterative testingDuring developmentEach part (module) is tested as it is written. Errors are fixed and the part is tested again, repeatedly.
Final / terminal testingAt the end of developmentThe whole program is tested together, to check all the parts work together and it meets every requirement.

Test data

def valid_quantity(q):
    return 1 <= q <= 10

tests = [(5, "normal"), (1, "boundary"), (10, "boundary"), (0, "invalid"), (11, "invalid")]
for value, kind in tests:

Refining algorithms

After testing, an algorithm is refined: errors are fixed, validation is added, and it is made more efficient (e.g. stopping a search as soon as the item is found), or changed to meet a new requirement. In the exam, "refine" means rewrite the algorithm so it does something better or extra.

★ EXAM TIP: TEST DATA

  • Give an actual value, not a description: write "11", not "a number that's too big".
  • Boundary data in OCR mark schemes is usually the valid value at the edge (1 and 10 here).
  • Invalid = right type, wrong value. Erroneous = wrong type.
Iterative testing
Testing each part of a program repeatedly during development, fixing errors as they are found.
Final testing
Testing the whole program at the end of development to check it meets the requirements (also called terminal testing).
Normal data
Typical, valid test data that the program should accept.
Boundary data
Valid test data at the edge of the allowed range.
Invalid data
Test data of the correct type that is outside the allowed range and should be rejected.
Erroneous data
Test data of the wrong data type that should be rejected.
Test plan
A table listing each test, its purpose, the test data, the expected result and the actual result.

Exam-style questions

Allow about 30 minutes. Answer each question before you look at its mark scheme.

Give two ways a programmer can anticipate misuse of a program.

  • Any two: validate inputs; check for division by zero; limit login attempts; authentication; reject inputs that are too long; sanitise inputs to stop SQL injection; menus that only allow valid choices.

A website asks users to enter a date of birth as DD/MM/YYYY. Describe three validation checks that could be used.

  • Any three, 1 each: presence check that something has been entered; format check that it matches DD/MM/YYYY; length check that it is 10 characters; range check that day is 1–31 / month 1–12 / year is sensible; type check that the day, month and year are numbers.

Write an algorithm that asks the user to enter a password and keeps asking until it is at least 8 characters long.

  • Input password (1).
  • Loop (while/do until) (1).
  • Condition checks length < 8 / >= 8 correctly (1).
  • Asks again inside the loop / error message (1).

Explain three ways to make a program easier to maintain.

  • Any three, each with an explanation, 1 each: comments explain what code does; meaningful variable names show what data is stored; indentation shows the structure; sub programs split code into manageable/reusable parts; constants mean values only change in one place.

Explain the difference between iterative testing and final testing.

  • Iterative testing happens during development, testing each module/part repeatedly as it's written (1).
  • Final testing happens at the end, testing the whole program together against the requirements (1).

A program asks for the number of people in a booking. It must be a whole number from 2 to 8. Give an example of normal, boundary, invalid and erroneous test data.

  • Normal: 3–7, e.g. 5 (1).
  • Boundary: 2 or 8 (1).
  • Invalid: e.g. 1, 9, 0, −4 (1).
  • Erroneous: e.g. "five", 4.5, a symbol (1).

The code if mark > 0 AND mark < 100 then should accept marks from 0 to 100. Identify the error and correct it.

  • It rejects the boundary values 0 and 100 / uses > and < instead of >= and <= (logic error) (1).
  • if mark >= 0 AND mark <= 100 then (1).

Explain why validation can't guarantee that data is correct.

  • Validation only checks data is sensible/follows rules (1) so a wrong value that is still within the rules, e.g. typing 15 instead of 16 for an age, will be accepted (1).
