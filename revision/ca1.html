1.1 Computational thinking

Computational thinking is a way of approaching a problem so that the solution can be expressed clearly enough for a computer, or another person, to carry it out. It is used at the start of any development task, when a problem is complex or unfamiliar, and when a solution needs to be explained to a team.

Benefits (1.1.3)Drawbacks
  • Complex problems become manageable
  • Solutions are logical and repeatable
  • Parts of a problem can be shared out across a team
  • Reuse of existing solutions saves time
  • Errors are easier to find in small parts
  • Takes time up front before any code is written
  • Over-simplifying (too much abstraction) can miss important detail
  • Not every problem suits a step-by-step approach, e.g. creative design decisions
  • Needs practice and skill to do well

The four components (1.1.4–1.1.5)

ComponentWhat it meansBenefitsDrawbacks
DecompositionBreaking a problem down into smaller partsEach part is easier to solve, test and assignParts must be recombined; interfaces between parts can be missed
Pattern recognitionSpotting similarities within and between problemsReuse existing solutions; make predictionsFalse patterns lead to wrong assumptions
AbstractionKeeping what matters and removing unnecessary detailFocus on the essentials; simpler modelsRemoving too much makes the solution unrealistic
Algorithmic designWriting the step-by-step solutionClear, testable instructions that can become codeTime-consuming; errors in logic carry through to code

Decomposition (1.1.6–1.1.10)

Purpose: to make a large problem manageable, so each part can be understood, built and tested on its own and shared across a team.

Tasks of decomposition:

  1. Identify the main features of the problem.
  2. Characterise each feature: what does it need to do?
  3. Break the problem down into smaller, more manageable parts.
  4. Break the solution down into smaller, more manageable parts (modules, functions).

Pattern recognition (1.1.11–1.1.12)

Purpose: to spot what is the same so effort isn't repeated, and to use patterns to make predictions.

UseExample
Find and interpret trends and similarities within and between problems and processesRegistering for a gym app and a library app both need: enter details, validate, confirm email.
Find common features between a given problem and existing solutionsA new booking system for a barber's is similar to an existing restaurant booking system, so its design can be adapted.
Make predictions and assumptions based on identified patternsWebsite traffic rises every Friday evening, so add server capacity on Fridays.

Abstraction (1.1.13–1.1.16)

Purpose: to focus only on what matters for the problem. The London Underground map is the classic example: it keeps stations, lines and connections and removes real distances and geography.

Tasks: identify information that is needed; filter out unnecessary details; hide details of internal workings (e.g. you call sort() without needing to know how it works).

Using abstraction: ask...Example: parking charge machine
What inputs are needed?Number plate, arrival time, departure time
What are the expected outputs and outcomes?Charge displayed; ticket/receipt; barrier opens after payment
What will vary?Length of stay, number plate, payment method
What will remain constant?Hourly rate, maximum daily charge, free period of 20 minutes
What key actions must the solution perform?Calculate time parked, calculate charge, take payment
What processes are repeated?Calculating the charge for every car; reading plates at entry and exit
What is filtered out?Car colour, driver's name, make of car

★ EXAM TIP: INTERRELATIONSHIPS (1.1.17)

  • The components feed into each other: decomposition produces small parts; pattern recognition spots which parts are similar; abstraction strips each part to its essentials; algorithmic design writes the steps.
  • Judge suitability: a small, familiar problem may need little decomposition; a large new system needs all four.

1.2 Algorithmic design

An algorithm is a finite, ordered set of unambiguous instructions that solves a problem. Characteristics: clear and unambiguous steps; a defined start and end; inputs and outputs; finite (it stops); correct (it solves the problem). Purpose: to plan a solution before coding, communicate it to others, and check the logic.

Flowcharts (1.2.2)

Worked example: one algorithm in three notations

A login allows three attempts at a password before locking the account.

Written description with hierarchical markers

StepInstruction
1Set attempts to 0
2Repeat:
2.1Input password
2.2If password is correct:
2.2.1Output "Welcome" and stop
2.3Otherwise add 1 to attempts
2.4If attempts equals 3:
2.4.1Output "Account locked" and stop

Code

PASSWORD = "Leeds2026"
attempts = 0
while True:
    password = input("Password: ")
    if password == PASSWORD:
        print("Welcome")
        break
    attempts = attempts + 1
    if attempts == 3:
        print("Account locked")
        break

Tracing, finding and correcting errors (1.2.7–1.2.10)

To find the purpose and output of an algorithm, trace it with sample input. This algorithm should output the largest number entered, stopping when 0 is entered.

StepInstruction
1Set largest to 0
2Input number
3While number is not 0:
3.1If number < largest, set largest to number
3.2Input number
4Output largest
Trace it with inputs 4, 9, 2, 0 yourself, then click to check.

Trace with inputs 4, 9, 2, 0: largest stays 0 every time because no number is less than 0. Output: 0. Error: step 3.1 uses < instead of >. Correction: 'If number > largest, set largest to number'. A further problem: if every number is negative, largest stays 0. Better: set largest to the first number entered.

Corrected in Python

number = int(input("Number (0 to stop): "))
largest = number
while number != 0:
    if number > largest:
        largest = number
    number = int(input("Number (0 to stop): "))
print("Largest:", largest)

★ EXAM TIP: DRAWING FLOWCHARTS

  • Use the correct symbol for every step: inputs and outputs go in parallelograms, decisions in diamonds.
  • Every decision needs two labelled exits (Yes/No or True/False).
  • Start and end with terminators. Use arrows on every line.
  • A loop in a flowchart is an arrow back up to an earlier step; check it can actually end.

Root cause analysis (1.3.3–1.3.4)

Purpose: to find and fix the real cause of a problem so it does not happen again, instead of repeatedly treating symptoms. Used after incidents, repeated faults, outages, or failed releases.

Five whys

QuestionAnswer
Why did customers get charged twice?The payment request was sent twice.
Why was it sent twice?Users pressed 'Pay' again because nothing appeared to happen.
Why did nothing appear to happen?The page took 12 seconds to respond with no loading message.
Why did it take 12 seconds?The payment API call waits for a slow fraud check.
Why is there no protection against double submission?The button isn't disabled after the first click. Root cause.

Benefits: quick, simple, no special tools. Drawbacks: can stop at a symptom; depends on the knowledge of the people asking; may miss multiple causes.

Top-down
Starting with the whole problem and breaking it into smaller sub-problems.
Bottom-up
Starting with small, detailed components and combining them into a larger solution.
Modularisation
Splitting a solution into self-contained modules that can be developed and tested separately.
Root cause analysis
A process for finding the underlying cause of a problem, rather than just treating the symptoms.

Failure mode and effects analysis (FMEA)

FMEA lists each way a part could fail, the effect, and scores severity, occurrence (likelihood) and detection (how hard to spot) from 1–10. Multiplying them gives a risk priority number (RPN) to rank what to fix first. It is usually done before problems happen.

ComponentFailure modeEffectSODRPNAction
Login serviceDatabase unavailableNo one can log in93254Add replica database
Payment formDouble submissionCustomer charged twice756210Disable button after click
Image uploadFile too largeUpload fails with no message46372Validate size and show error

Try it: RPN calculator

Event tree analysis (ETA)

ETA starts from a single initiating event and branches at each safeguard into success or failure, showing every possible outcome. It shows whether safeguards are enough.

Actions after root cause analysis

ActionWhen
LogRecord the problem, cause and fix in an incident or fault log so trends can be spotted and the knowledge kept.
CloseThe cause is fixed and tested; the ticket is closed and the user informed.
EscalateThe problem is beyond your authority or skill: pass to a manager, a specialist (e.g. the network team) or an external third party (e.g. the software vendor).

  • Process (rectangle)

ALGORITHM NOTATIONS

  • Flowchart: visual, but large ones get messy
  • Written description: hierarchical markers 1, 1.1, 1.1.1; can be ambiguous
  • Code: precise and testable; needs programming knowledge

PROBLEM-SOLVING APPROACHES

  • Top-down: whole → parts
  • Bottom-up: parts → whole
  • Modularisation: self-contained modules, built in parallel

ROOT CAUSE ANALYSIS

  • Five whys: quick, may stop at a symptom
  • FMEA: severity × occurrence × detection = RPN; done before failure
  • Event tree: one event, branches for each safeguard
  • Then: log, close or escalate

A bank is launching a new mobile app. Evaluate the use of FMEA and the five whys for managing problems with the app.

Indicative content:

  • FMEA: done before launch; systematically lists failure modes (login fails, payment errors, data exposure); prioritises by severity, occurrence, detection; important for a bank where failures affect money and regulation. But time-consuming, needs expertise, scores can be subjective, may miss unforeseen failures.
  • Five whys: quick and cheap after a problem occurs; good for individual incidents reported by customers. But may stop at a symptom; relies on staff knowledge; not suited to complex problems with several causes; reactive.
  • Interrelationship: FMEA reduces likely failures before launch; five whys handles problems that still occur.
  • Judgement: e.g. both should be used: FMEA before launch because of the high stakes for a bank, five whys for incidents after launch.

Discuss the benefits and drawbacks of modularisation for a team of six developers building an online shop.
